# Issue 11 - 簡單 Telegram 問答觸發多棒重複調查，造成回覆延遲

## 概述
讓已有足夠資訊的簡單問答能直接收尾，避免後續角色重複啟動完整調查；保留複雜操作必要的查證。

修復順序：第 1 項；順序為建議排程，不要求互不相依的調查等待。

## 已確認證據與重現
2026-10-08 12:41（台灣時間）的唯讀觀測：訊息 #1297「所以沒辦法跑成功嗎」尚無最終 assistant 回覆；chat_live_events 顯示前一棒已形成結論，後續 Explorer 又讀取排程資料、Git 與進度檔，等待超過 10 分鐘。此為歷史觀測，不代表建立 issue 時仍在執行。

證據來源：RunWuKong 部署中的唯讀 SQLite 查詢、docker logs、docker top 與 /data/settings.json 的 agent 欄位；沒有保存或揭露 token。

```sql
SELECT id, job_id, status, started_at, finished_at, message
FROM scheduler_runs WHERE started_at >= 1791393535 ORDER BY id;
SELECT id, role, status, created_at, content FROM chat_messages
WHERE thread_id = 'scope:user:tg-915354960' AND created_at >= 1791393535 ORDER BY id;
```

上述為歷史觀測的查詢範圍；後續查核需另外記錄取數時間，不把新增回合算入歷史統計。

最小重現與首要驗證：以固定簡單追問、新資訊查詢與複雜操作三組對照，記錄計畫角色、各棒輸入輸出及工具呼叫；先確認測試能抓到重複調查與省略必要查證兩種失敗。

## 程式碼現況與方案草案

2026-10-08 唯讀檢查工作區程式碼：

- `run_turn_traced_with_attachments` 已取得相關記憶與上一回合記憶，但呼叫 `plan_skill_chain_with_preferences` 時只傳本次 `input`；planner 沒有收到這些上下文。
- `skill_planning_prompt_with_preferences` 已要求簡單任務一棒、最多三棒，但未明確界定有上下文的狀態追問。
- 執行器逐一執行所有計畫步驟，透過 `chain_context` 傳遞前棒輸出；目前沒有依前棒文字宣稱完成而跳過後棒的機制。
- 上述是程式碼事實；尚不能證明 planner 缺上下文是唯一根因，也未取得修復前後對照。

建議方案 A：讓規劃可利用有界、可追溯的追問上下文，明確區分簡單追問、新資訊查詢與複雜操作。已有足夠上下文且不要求新查證／操作的追問只規劃一棒；資料不足時進行必要查證，不能猜測。內部如何提供上下文待基線測試後決定。

比較方案 B：維持原多棒規劃，新增執行中完成判定以跳過後棒。此方案必須證明前棒足以完成使用者目標，否則可能跳過驗證。2026-10-08 使用者接受方案 A；不採方案 B，也不新增通用完成判定架構。

## 邊界
不在本 issue 直接全面更換模型、延長逾時或重設架構。測試使用獨立 scope 與臨時工作目錄，不干擾正式任務。三個服務存活不等於任務交付成功。
