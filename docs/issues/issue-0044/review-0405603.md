### SHOULD FIX

**S1. 壓縮失敗或被丟掉時，server 端的壓縮不會被中止**
- 位置：`crates/wukong-gateway/src/opencode_server.rs:765-785`（`compact_session`）
- 狀況：一般回合會掛 `InterruptOnDrop`，失敗時呼叫 `abort_session`；壓縮兩者都沒有
- 什麼情況會發生：
  - 上游連不到，壓縮的 RetryWatch 90 秒後放棄
  - `hold_session_lease` 拿不到續租，丟掉壓縮的 future
- 結果：V2 在 server 上繼續重試那次壓縮。下一個回合的 prompt 排在它後面，要再等 90 秒才由回合自己的 RetryWatch 中止並送 interrupt
- 只影響常駐 server 模式。本機模式在操作結束時會回收整個 serve
- 建議：與 `run_streaming` 相同，送出 compact 後掛 `interrupt_on_drop`，`consume_event_stream` 回錯誤時呼叫 `abort_session`；再補一支假 V2 測試，斷言壓縮失敗後有 `POST …/interrupt`

**S2. `opencode-state` 的備份檔含 provider 憑證，卻以預設權限寫在部署目錄**
- 位置：`scripts/install.sh:689-690`（`backup_docker_state` 以 `> "$archive"` 建立 tar），以及 rollback 另存的 `.wukong-backups/<前一版>-rollback-<時間>/volumes/`
- 內容：volume 裡有 `auth.json`（provider 的 API key，演練記錄的 nvidia 憑證就在裡面）與完整的對話資料庫
- 權限：以 installer 預設的 umask，tar 是 0644，目錄是 0755。原本這些資料只在 docker volume 裡，一般使用者讀不到
- 影響：在多人共用的主機上，部署目錄的上層可以進入時，其他本機使用者就讀得到憑證與對話。單人主機、家目錄 0750 時風險低
- 建議：建立 `volumes/` 與 tar 時用 `umask 077`，或事後 `chmod 700`／`chmod 600`；再在 installer 測試加一個權限斷言
- `.env` 也是 0644（演練「觀察」已記，屬既有狀況），可以一起處理：installer 產生或改寫 `.env` 時設為 0600

**S3. 演練觀察到 free-limit 429 約 161 秒才回報，與「重試超過 90 秒就中止」（TBD-3）沒有對照清楚**
- 位置：`docs/issues/issue-0044/rehearsal.md`「觀察」第 2 點
- 現有證據：
  - SCN-007 第一列（限流）的分類正確，也沒有變成 agent timeout，這列本身成立
  - TBD-3 的決定是「任何 retry 持續超過 90 秒就中止」。161 秒沒被中止的可能原因有兩個，這次沒查清楚：
    - V2 對 429 是在內部等待，不送 `session.retry.scheduled`
    - 重試之間有 `step.ended` 之類的事件，讓 `RetryWatch.recovered()` 重新起算
  - 第二種情況代表「放棄」條件會被某些錯誤類型繞過。目前只有 transport 錯誤以真實 V2 驗證過 91 秒結束（`probe-retry.md`）
- 建議：下次拿到真實的 429 時，保存 `/api/event` 樣本，確認是哪一種，並把結論寫進 README `## 待確認事項`。如果是第二種，`recovered()` 的條件要排除失敗步驟的 `step.ended`
