# Web History And Schedule Settings Design

## Context

`wukong-web` is a small plain vanilla web app served by Axum. The current UI is a single static shell with two custom elements: `<wukong-chat>` and `<wukong-settings>`. The chat route streams answers through `/chat?q=...`, and Telegram settings are managed through `/api/settings`.

The existing `wukong-memory` database stores recallable memory events, including `User: ...` and `Assistant: ...` rows for each turn. That data is not a suitable source for a messaging-style history UI because it has no durable conversation/thread model, no formal user/assistant pairing, no UI-specific pagination contract, and may be affected by memory consolidation or pruning. Web chat history should therefore use dedicated tables while keeping `memories` for AI recall.

The scheduler already exists in `wukong-scheduler` and is managed by the CLI. The web UI should expose a read/basic-management surface over the existing `SchedulerStore` rather than reimplementing scheduling.

## Goals

- Add a lightweight route mechanism while preserving the plain vanilla web architecture.
- Provide a messaging-app-like chat history view.
- Lazy-load older chat messages 10 at a time when the user scrolls upward.
- Support jumping to messages around a specified date.
- Store web chat history separately from recall memory.
- Add a schedule settings page that can list, enable, disable, and delete existing scheduled jobs.
- Add a system settings page with useful runtime and scheduler summary information.

## Non-Goals

- Do not migrate historical `memories` rows into chat history in the first version.
- Do not build a full SPA framework or introduce a frontend build step.
- Do not add schedule creation, editing, or manual trigger in the first version.
- Do not replace existing `memory.remember()` behavior.

## Routes And Layout

Use hash routes to keep static serving and Axum fallback behavior simple.

- `#/chat`: main chat view with live messaging, lazy-loaded history, and date jump.
- `#/settings`: redirects to `#/settings/telegram`.
- `#/settings/telegram`: existing Telegram settings.
- `#/settings/system`: system and runtime summary.
- `#/settings/schedules`: scheduled job list and basic management.
- Unknown hash routes show a compact not-found state with links back to chat and settings.

The frontend remains plain vanilla web components. `index.html` becomes an app shell with a header/nav and a main outlet. `app.js` owns the small router and mounts only the component needed by the active route. This avoids all route components loading data or binding events at the same time.

Primary navigation contains `對話` and `設定`. Settings routes include secondary navigation for `Telegram`, `系統`, and `排程`.

Desktop and mobile both use a single-column chat experience. Settings pages use card-style content. On mobile, the chat composer remains reachable at the bottom of the chat view.

## Chat History Storage

Add dedicated chat history tables in the same SQLite database used by the web process.

`chat_threads`:

- `id TEXT PRIMARY KEY`
- `scope TEXT NOT NULL`
- `title TEXT NOT NULL`
- `created_at INTEGER NOT NULL`
- `updated_at INTEGER NOT NULL`

`chat_messages`:

- `id INTEGER PRIMARY KEY AUTOINCREMENT`
- `thread_id TEXT NOT NULL`
- `role TEXT NOT NULL`
- `content TEXT NOT NULL`
- `content_html TEXT`
- `status TEXT NOT NULL`
- `created_at INTEGER NOT NULL`

First version uses one default thread per scope. The user does not need to understand or manage threads; the UI behaves as one continuous chat timeline. Keeping `thread_id` in the schema leaves room for future multi-thread history.

`role` values are `user`, `assistant`, and `system`. First version primarily writes `user` and `assistant`. `status` values are `complete` and `error`.

Assistant `content_html` stores HTML generated by `wukong_render::to_web_html()`. User content is always rendered through escaping on the frontend and is not trusted HTML.

## Chat History API

All endpoints use the existing `token` query parameter authorization behavior.

- `GET /api/chat/messages?limit=10`
  - Returns the latest messages for the default scope thread.
- `GET /api/chat/messages?before=<message_id>&limit=10`
  - Returns older messages before the given message id.
- `GET /api/chat/messages?date=YYYY-MM-DD&limit=10`
  - Returns messages around the requested local date.

`limit` defaults to 10 and is capped server-side.

The existing `/chat?q=...` SSE endpoint can remain the first-version send path. During the SSE handling flow, the server records the user message before running the turn and records the assistant message when the final answer is produced. If the turn fails, the server records an assistant message with `status = error` and the user-facing error content.

## Chat UI Behavior

- On `#/chat`, load the latest 10 messages and scroll to the bottom.
- When the user scrolls near the top, request the next 10 older messages using `before`.
- After older messages are prepended, preserve the user’s visual scroll position so the viewport does not jump.
- New user messages appear immediately as user bubbles.
- During SSE, show the existing progress bubble and reasoning details behavior.
- When SSE completes, replace the progress state with the final assistant bubble and rely on the stored message for future reloads.
- Date jump clears the current list, loads messages around the selected date, and shows date separators.
- Date separators use labels such as `2026 年 6 月 17 日`.
- Empty history shows `還沒有對話，問悟空第一個問題。`
- No messages for a selected date shows an empty-date state rather than an error.

## Schedule API

Use the existing `wukong-scheduler::SchedulerStore` against the configured database URL.

- `GET /api/schedules`
  - Lists all jobs with frontend-friendly fields.
- `POST /api/schedules/:id/enable`
  - Enables a job and recalculates `next_run_at`.
- `POST /api/schedules/:id/disable`
  - Disables a job and clears `next_run_at`.
- `DELETE /api/schedules/:id`
  - Deletes a job.

Schedule response fields:

- `id`
- `name`
- `kind`
- `scope`
- `prompt` for turn jobs
- `task` for maintenance jobs
- `cron`
- `enabled`
- `next_run_at`
- `last_run_at`

First version does not create, edit, or manually trigger schedules.

## Schedule UI

Route: `#/settings/schedules`.

The page lists scheduled jobs as cards or a compact table depending on viewport width. Each item shows:

- name
- type: turn job or maintenance job
- scope
- cron expression
- enabled state
- next run time
- last run time
- actions: enable/disable and delete

Delete requires confirmation before calling the API. Successful operations reload the schedule list. Empty state says `目前沒有排程，可先用 CLI 建立排程。`

## System Settings UI

Route: `#/settings/system`.

Show useful runtime summary data:

- current scope
- whether web token authorization is enabled
- memory database status when available
- total scheduled jobs
- enabled scheduled jobs
- nearest next scheduled run time

The system page is read-only in the first version.

## Error Handling And Authorization

- All new APIs use the existing token query parameter authorization.
- Unauthorized requests return `401`; frontend displays `沒有權限讀取資料。`
- Database and scheduler failures return `500`; frontend shows a concise error message.
- Chat history load failure preserves current messages and shows a retryable error near the top.
- Date jump with no data is an empty state, not an error.
- Schedule operations returning no changed row should surface `找不到排程。`
- Backend deletion must target a single schedule id.

## Testing

Rust API tests:

- Unauthorized requests cannot read chat history or schedules.
- `GET /api/chat/messages` returns the latest 10 messages by default.
- `before` pagination returns the next older 10 messages.
- `date` lookup returns messages around the requested date.
- Sending a web chat turn records user and assistant messages.
- `GET /api/schedules` lists existing scheduler jobs.
- Schedule enable, disable, and delete update `SchedulerStore` state.

Frontend/manual verification:

- Route switching works on desktop and mobile.
- Chat history loads latest messages on entry.
- Upward scrolling loads older messages without jumping the viewport.
- Date jump loads the selected date context.
- Schedule enable, disable, and delete work and refresh the list.
- Token-enabled mode authorizes all new API calls correctly.

## Recommended Implementation Order

1. Add chat history store/schema and API tests.
2. Persist web chat messages from the existing SSE flow.
3. Add route shell and route-specific component mounting.
4. Update chat component for initial history load, upward pagination, and date jump.
5. Add schedule API over `SchedulerStore`.
6. Add schedule settings component.
7. Add system settings component and settings sub-navigation.
8. Run Rust tests and manual browser verification.
